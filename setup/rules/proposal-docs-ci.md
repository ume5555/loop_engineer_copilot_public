# 着手時の提案のドキュメントと CI（中規模・大規模のときだけ読む）

PC 全体のルール（`setup/copilot-instructions.user.md` を配置したもの）の「作業の着手時」の節から外へ出した詳細。中規模と大規模の提案を書く前に読む。
このファイルは配置されず、clone から直接読まれる。下のコマンドの `<clone>` は、このファイルがあるリポジトリのルート
（PC 全体のルールの「参考にするリポジトリ」に書いてあるローカルの clone のパス）に置き換える。

## ドキュメントの一覧と、実装前のレビュー

一覧の候補は次の 3 つ。その作業に当てはまる行だけを出す（候補を増やさない）:

- 仕様書: 実装前。置き場の PROGRESS.md の目的・完了条件・やらないこと・前提がそのまま仕様書（別の文書は作らず、PROGRESS.md を正とする。リポジトリには入らないので、レビューは置き場のファイルを示して受ける）
- テスト仕様書: テストコードを書いた直後に未実施の版、実装後に合否入りで再生成。テストコードと検証コマンドの出力から生成器が作る。
  生成器（`loop-harness/bin/test-spec.mjs`）はこのリポジトリに無く、loop_engineer の clone（Claude Code 版。生成器は Node.js のスクリプトなので Claude Code 自体は要らない）にある。無い PC ではこの行を出さない。
  テストを先に書かない作業（見た目、手探りの改修）では「実装後のみ」と出す
- 設計メモ: 実装前。大規模だけ。タスク一覧・依存順・モジュール間の約束を `docs/design.md` に書く

返事の受け方（PROGRESS.md の「ドキュメント」欄に書いて引き継ぐ）:

- 「作る」: 選ばれた文書を完了条件の番号に写す。実装前に作れるものは実装前に作り、**場所を示して止まり、ユーザーのレビューと了承を待ってから実装に入る**。
  レビューで直すときは生成物を手で直さず、生成元（PROGRESS.md、テストコードの項目名。項目名は「前提条件 → 期待結果」の形）を直して再生成する。
  テスト仕様書の未実施の版は `node <loop_engineer の clone>/loop-harness/bin/test-spec.mjs --target <作業対象> --planned --verify "<検証コマンド>"`（検証コマンドは実行されない）。
  実装後、最終報告の前に `--planned` を外して同じ出力先（`docs/test-report/test-spec.md`）へ再生成し、場所を報告する（以後テストを追加・変更するたびに同じ。差し戻すフックは無いので自分で確かめる）
- 「後回し」: 止まらずに実装へ進む。残課題が無くなり完了条件をすべて照合できたら、最終報告に同じ一覧（実装後に作れるもの）を出して 1 回だけ確認する。
  了承されたら上のコマンドから `--planned` を外して実行し、場所を報告する。「ドキュメント」欄が無い既存プロジェクトで中規模以上の作業をしたときも同じ扱い
- 「要らない」: PROGRESS.md の「やらないこと」に書く。最終報告でも聞かない
- ドキュメントに触れずに「すすめて」と返されたら「後回し」として扱う

## CI を入れるかの提案

提案には、見立て（入れる寄り／要らない寄りと根拠）と内容の案を 2〜3 行で書く。プロジェクトを見て決め、見ても分からない項目は既定を置く:

- 見立ての目安。入れる寄り: GitHub の remote があり PR で進める、検証コマンドが非対話でクリーンな環境でも動く、複数の OS で動かす、複数の人か PC から push する。
  要らない寄り: remote が無い、main へ直接 push する、検証にローカルだけの資源（GUI、実機、秘密情報、有料 API）が要る、使い捨ての試作。
  private のリポジトリなら GitHub Actions の無料枠を消費することを 1 行添える
- 内容の案は 4 項目: 走らせるもの（PROGRESS.md の検証コマンドにあるものだけ。lint や型チェックを AI から足さない。足りないと思ったら残課題に書く）、
  いつ走るか（既定は PR と main への push）、どの環境で（既定は Ubuntu だけ。OS とランタイムの版）、CI に入れない検証と理由。
  デプロイ、リリース、キャッシュの調整、脆弱性の検査は案に含めない（頼まれたら別の作業として扱う）

返事の受け方（PROGRESS.md の「CI」欄に書いて引き継ぐ）:

- 「入れる」: 完了条件の番号に写し、決めた内容を欄に書く。Node.js のプロジェクトなら雛形から作る:
  `node <clone>/setup/new-project.mjs <作業対象> --verify "<検証コマンド>" --ci`
  （`--ci-os ubuntu,windows`、`--ci-on pr,push`、`--ci-node <版>`、`--ci-run "<コマンド>"` で内容を変える。できるのは `.github/workflows/verify.yml`。既にあるファイルは上書きされない）。
  ほかのスタックは同じ 4 項目で手で書く。入れたあと最初の PR で CI が落ちたら、同じブランチで直す（環境の差は入れてみるまで分からない）
- 「後回し」「要らない」: 理由と一緒に欄に書く。以後の作業では聞かない（ユーザーが「CI を入れて」と言ったら、その時点で内容の案を出す）
- CI に触れずに「すすめて」と返されたら「後回し」として扱う
